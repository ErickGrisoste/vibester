# Scrapping Service

> Contexto específico do microserviço de scraping/estimativa de movimento de estabelecimentos do Vibester.
> Este documento complementa o `CLAUDE.md` da raiz do monorepo. Em caso de conflito, o `CLAUDE.md` raiz prevalece nas diretrizes gerais de produto/arquitetura; este arquivo prevalece em convenções específicas deste serviço. Código-fonte é sempre a fonte de verdade final.
>
> **Atenção**: este serviço é, na prática, um **worker com cron interno** (não um serviço HTTP CRUD como os outros três já documentados). A superfície HTTP existe apenas como camada auxiliar (health check, consulta pontual, endpoint utilitário de descoberta de lugares, métricas) — o núcleo do serviço é o job agendado em `src/jobs/movement.job.ts`. Não infle este documento com convenções de rota que não existem; e não copie padrões de outro serviço sem verificar contra o código real aqui.

---

## Responsabilidade do Serviço

O `scrapping-service` é responsável exclusivamente por:

- rodar, a cada hora (`0 * * * *`, cron via `node-cron`, timezone `env.timezone`), um job que:
  1. busca a lista de estabelecimentos abertos no `establishment-service` via HTTP (`GET {ESTABLISHMENT_SERVICE_URL}/establishments/open`, ver `EstablishmentClient.listOpenEstablishments`);
  2. para cada estabelecimento com `googlePlaceId`, consulta a SerpAPI (engine `google_maps`) para obter popularidade ao vivo (`live_busyness_score`) e o histórico horário do dia (`popular_times`), com a resposta validada por Zod (ver `SerpApiService`, seção Segurança #10). **A URL não deve incluir `type=place` nem `gl=br`** — confirmado empiricamente (setembro/2026) que a SerpAPI omite `popular_times` da resposta quando qualquer um desses dois parâmetros está presente, mesmo para um `place_id` que tem esse dado no Google Maps; a consulta só por `engine=google_maps` + `place_id` + `hl=pt-BR` já é suficiente e específica (place_id já é único globalmente). Não reintroduza esses parâmetros "pra ficar mais completo" sem re-testar contra a API real primeiro;
  3. calcula o movimento (`computeMovement` em `movement-engine.ts`) a partir do score ao vivo — ou, se ausente, da **mediana** das amostras históricas do mesmo dia da semana/hora dos últimos `POPULAR_TIMES_RETENTION_DAYS` (28 dias, tabela `popular_times_daily`), mínimo de 3 amostras; menos que isso vira `UNAVAILABLE`. O score ao vivo passa por suavização (EMA, α=0.6, contra o score suavizado do ciclo anterior) e a troca de faixa (`VERY_LOW`…`VERY_HIGH`) passa por histerese (uma margem de 3 pontos perto do limiar não troca a faixa se a mudança for de banda vizinha — mudanças maiores aplicam na hora). O resultado inclui um `confidence` (0–1: 1.0 para score ao vivo; 0.5×proporção de amostras/4 para estimado — 4, não 7, porque uma janela de 28 dias só cabe até 4 ocorrências do mesmo dia da semana) — ver `src/services/movement-engine.ts` para a implementação completa e `src/services/__tests__/movement-engine.test.ts` para os casos cobertos;
  4. quando o score é estimado (`isEstimated: true` / `source: "ESTIMATED"`), grava `statusText: "Estimativa baseada em histórico"`;
  5. persiste o resultado em `current_popularity` (upsert, 1 linha por estabelecimento, incluindo `confidence`) e o histórico horário em `popular_times_daily`;
  6. publica um evento Kafka `establishment.movement.updated` no tópico `establishments` para cada estabelecimento processado, incluindo `confidence` no payload (ver seção Kafka do `establishment-service/CLAUDE.md` — este serviço é o produtor daquele evento);
  7. remove registros de `popular_times_daily` com mais de 28 dias no início de cada execução (`cleanOldPopularTimesDaily`) — o mesmo número (`POPULAR_TIMES_RETENTION_DAYS` em `movement.service.ts`) é usado tanto para a limpeza quanto para a janela de busca do fallback (item 3); não altere um sem o outro.
- expor uma superfície HTTP secundária (Fastify), protegida por JWT (exceto `/health`):
  - `GET /health` — checagem de banco (`SELECT 1`);
  - `GET /places/:placeId/popularity` — consulta pontual à SerpAPI por `placeId` (não passa pelo pipeline do job, não grava nada no banco);
  - `GET /movements/:establishmentId` — lê o último `current_popularity` já persistido (com cache em memória de 5 min) e anexa um campo `freshness` (`FRESH`/`STALE`/`EXPIRED`) calculado em tempo de leitura a partir de `updatedAt` (`computeFreshness` em `movement-engine.ts`) — **não** é persistido, é sempre recalculado a partir de "agora"; o campo `level` retornado nunca é reescrito por causa do freshness (é aditivo, não muda o significado do que já existia);
  - `GET /places/nearby` — busca lugares próximos (`bar`/`night_club`/`restaurant`/`cafe`), usada para descobrir candidatos a estabelecimento — não cria nada no banco, apenas retorna a lista. **Fonte principal é a SerpAPI** (`SerpApiService.searchNearbyPlaces`, engine `google_maps` no modo `type=search`, uma query por tipo — `bar`→"bar", `night_club`→"balada", `restaurant`→"restaurante", `cafe`→"café") — não exige billing do Google Cloud e já devolve o Google Place ID de verdade, o mesmo usado por `getPlacePopularity`. **Google Places (`GooglePlacesService`) é fallback**, só chamado pelo controller (`place.controller.ts`) se a SerpAPI lançar exceção — mantido de propósito para não deixar o serviço 100% dependente de um único fornecedor externo (exige `GOOGLE_API_KEY` com billing habilitado pra funcionar de verdade quando acionado);
  - `GET /metrics` — métricas Prometheus (sem `authenticate`, mesmo padrão do `establishment-service`); ver seção Observabilidade.

**Importante**: hoje este serviço **só produz** eventos Kafka de movimento — não existe nenhuma chamada HTTP síncrona (`PATCH`/`POST`) deste serviço para o `establishment-service` no código atual (o único fetch para lá é o `GET /establishments/open` de leitura). Se o `establishment-service/CLAUDE.md` mencionar um caminho HTTP síncrono de atualização de movimento vindo daqui, verifique o código de ambos os lados antes de assumir que ele ainda existe — não reintroduza uma chamada `PATCH` "para bater com a documentação" sem confirmar a necessidade.

Nunca adicione regras de negócio de perfil de estabelecimento, autenticação, feed ou pagamento aqui. Se uma feature parece pertencer a outro domínio, ela deve ser feita no serviço correspondente e comunicada via Kafka.

## Stack e Dependências deste Serviço

- Fastify 5 + `@fastify/cors`, `@fastify/jwt`, `@fastify/rate-limit`, `@fastify/swagger` (+ `swagger-ui`) — usados só pela superfície HTTP secundária, não pelo job.
- **`node-cron`** — agendamento do job principal (`src/jobs/movement.job.ts`), único serviço do monorepo documentado até agora que roda um cron **dentro do próprio processo** (não há `CronJob` do Kubernetes).
- Prisma 7 com `@prisma/adapter-pg` (driver adapter sobre `pg.Pool`), mesmo padrão dos outros serviços — mas com uma particularidade: o `generator client` em `prisma/schema.prisma` usa `output = "../src/generated/prisma"` (client gerado dentro de `src/`, não no local padrão do `node_modules`), o que exige um passo extra de cópia no `Dockerfile` (ver seção Infra).
- PostgreSQL — únicas tabelas: `current_popularity` (estado atual, 1 linha por estabelecimento) e `popular_times_daily` (histórico horário, usado para a estimativa de fallback).
- Kafka (`kafkajs`) — **produtor apenas** (`establishments` / `establishment.movement.updated`), sem consumidor neste serviço (mesmo padrão do `auth-service`).
- **Sem Redis** — diferente do `user-service`/`establishment-service`; o cache é só em memória (`TTLCache`, `src/utils/cache.ts`), usado em `SerpApiService` (30 min por `placeId`) e em `MovementService.getMovementByEstablishmentId` (5 min por `establishmentId`).
- `zod` — usado para validar `env` (`src/config/env.ts`, fail-fast no boot), a querystring de `GET /places/nearby` (`src/schemas/nearby-places.schema.ts`) e a resposta da SerpAPI (`serpApiResponseSchema` em `serpapi.service.ts`); as demais rotas usam JSON Schema do Fastify.
- `prom-client` — métricas Prometheus expostas em `GET /metrics` (mesmo padrão do `establishment-service`: `Registry` próprio em `src/config/metrics.ts`, `collectDefaultMetrics` + métricas HTTP genéricas + métricas específicas do job/scraping). Ver seção Observabilidade.
- `src/utils/retry.ts` (`fetchWithTimeout`) — wrapper próprio sobre o `fetch` global com timeout (`AbortSignal.timeout`, default 10s) e retry com backoff exponencial (default 3 tentativas, 500ms/1s/2s) — é o único mecanismo de HTTP usado neste serviço (SerpAPI, Google Places e a chamada interna ao `establishment-service`); não há `axios`/`got`/`undici` client dedicado.
- `src/utils/logger.ts` (`AppLogger`/`consoleLogger`) — logger mínimo próprio (JSON em `stdout`/`stderr`), usado pelo job e por `MovementService`/`SerpApiService`, desacoplado do `app.log` do Fastify (para que o job funcione mesmo fora do contexto de uma request). Os controllers HTTP (`movement.controller.ts`, `place.controller.ts`), porém, ainda usam `console.error` puro em vez desse logger — inconsistência real do código atual, não um padrão a copiar para arquivo novo: prefira `AppLogger`/`request.log` em código novo.

Não introduza um ORM alternativo, outro cliente Kafka, Redis, ou uma lib de scheduling diferente de `node-cron` sem necessidade real — reutilize o que já existe.

### Padrão de uma feature nova

Depende do tipo de mudança:

1. **Novo dado extraído/persistido pelo job** (ex.: mais um campo do SerpAPI): adicionar no tipo local de `serpapi.service.ts` (ou no service novo, se for outra fonte), mapear em `MovementService`, e migrar `prisma/schema.prisma` com índice equivalente se o campo for usado em filtro/agregação (seguir `@@index([establishmentId, dayOfWeek, hour])` como referência). Adicionar teste unitário em `src/services/__tests__/movement.service.test.ts` seguindo o padrão de mocks já existente (`vi.hoisted` + `vi.mock` de `prisma/index` e `kafka/producer`).
2. **Nova fonte externa de scraping** (ex.: outra API além de SerpAPI/Google Places): criar `services/<fonte>.service.ts` com sua própria classe, sempre usando `fetchWithTimeout` (nunca `fetch` cru) e cache `TTLCache` se a chamada for repetitiva/cara. Nunca deixe uma falha dessa fonte derrubar o loop principal do job — sempre dentro do `try/catch` por estabelecimento em `MovementService.updateMovementLevelsFromSavedEstablishments`.
3. **Nova rota HTTP**: schema em JSON Schema (seguindo `routes.ts`) ou Zod (seguindo `nearby-places.schema.ts`, se a validação for mais rica que tipos simples) + `onRequest: [authenticate]` se a rota expõe dado sensível ou é cara de rodar (padrão de `config.rateLimit` dedicado em `/places/nearby`, que é uma chamada paga — SerpAPI como principal, Google como fallback). Controller como função exportada, com `try/catch` retornando `500 { message: "..." }` genérico (seguir `getPlacePopularity`, não a ausência de try/catch de `getMovementByEstablishmentId`).
4. Testes: unitário do service + teste de integração da rota em `tests/integration/scrapping.integration.spec.ts` (arquivo único hoje — pode crescer, mas siga a mesma estrutura de mocks já usada nele).

## Segurança — obrigatório em qualquer alteração

1. **`src/config/env.ts` valida com Zod (`safeParse`) e falha rápido (`process.exit(1)`)**, mesmo padrão do `establishment-service`: `JWT_SECRET`, `DATABASE_URL`, `SERP_API_KEY`, `GOOGLE_API_KEY` e `ESTABLISHMENT_SERVICE_URL` são obrigatórios e o processo não sobe se algum estiver ausente/inválido. `TZ` continua opcional de propósito (o `node-cron`/`Intl.DateTimeFormat` cai para o timezone do sistema quando ausente — não é uma falha real). `CORS_ORIGIN`, `KAFKA_BROKERS`, `RATE_LIMIT_MAX`/`RATE_LIMIT_TIME_WINDOW` e `PORT` continuam com default (ver item 2 abaixo) — não são obrigatórios. Ao adicionar uma env var nova crítica, adicione-a ao `envSchema` em vez de ler `process.env` direto em outro arquivo.
2. **`CORS_ORIGIN` tem fallback para `"*"`** (`env.corsOrigin = process.env.CORS_ORIGIN || "*"`) — ao contrário dos outros serviços documentados, aqui o próprio código já cai para CORS aberto se a env não estiver setada. Garanta que `CORS_ORIGIN` esteja sempre definida no secret/config do k8s de produção; não dependa desse default para produção.
3. **JWT aplicado seletivamente**: todas as rotas exceto `/health` usam `onRequest: [authenticate]` (`src/routes.ts`), que faz `request.jwtVerify()` num try/catch e `reply.send(err)` em caso de falha. Preserve exatamente esse padrão (mesma função `authenticate`) em qualquer rota nova que precise de autenticação — não reimplemente a verificação inline.
4. **Todos os controllers têm `try/catch` + `500 { message: "..." }` genérico** (`getPlacePopularity`, `searchNearbyPlaces`, `getMovementByEstablishmentId`) — nunca vazar stack/erro interno do Prisma na resposta. Preserve esse padrão em qualquer controller novo.
5. **Chamadas a APIs externas sempre via `fetchWithTimeout`** (`src/utils/retry.ts`), nunca `fetch` cru — é o que garante timeout (10s) e retry com backoff em toda chamada a SerpAPI, Google Places e ao `establishment-service`.
6. **Nunca logar a `URL` completa das chamadas a SerpAPI/Google Places**: `SERP_API_KEY` e `GOOGLE_API_KEY` vão como querystring (`api_key=`/`key=`) na própria URL montada em `serpapi.service.ts`/`google-places.service.ts`. Hoje nenhum log imprime essa URL — se for adicionar log de request/debug nesses services, nunca logue `url.toString()` diretamente (logue no máximo o `placeId`/tipo buscado).
7. **Validação de entrada**: `GET /places/nearby` valida via Zod (`nearbyPlacesQuerySchema`, com `min`/`max`/`default` para lat/lng/radius) antes de chamar a SerpAPI/Google — qualquer parâmetro novo dessa rota deve entrar no schema Zod, não ser lido direto de `request.query`. As demais rotas usam JSON Schema do Fastify nos `params`; siga o schema já presente em `routes.ts`.
8. **Segredos**: `JWT_SECRET`, `DATABASE_URL`, `SERP_API_KEY`, `GOOGLE_API_KEY`, `KAFKA_BROKERS` sempre via secret do k8s (`scrapping-service-secret`), nunca hardcode. Este serviço não tem `.env.example` — se for criar um, siga o padrão de placeholders do `auth-service`.
9. **Evento Kafka publicado (`establishment.movement.updated`) não deve carregar dado sensível** — hoje carrega `eventVersion` (`MOVEMENT_EVENT_VERSION = 1`, campo de topo, fora de `data`), `establishmentId`, `level`, `source`, `confidence` e, opcionalmente, `category`; não adicione campos internos (ex.: `googlePlaceId` cru, dados de billing da SerpAPI) ao payload sem necessidade real do lado consumidor. Se um campo novo mudar o *significado* de um campo existente (não só adicionar informação), incremente `MOVEMENT_EVENT_VERSION` — o consumidor atual (`establishment-service`, zod sem `.strict()`) ignora campos desconhecidos silenciosamente, então campos aditivos não quebram nada, mas uma mudança de significado precisa ser sinalizada pela versão.
10. **Resposta da SerpAPI é validada por Zod** (`serpApiResponseSchema` em `serpapi.service.ts`) antes de ser usada — se o shape vier diferente do esperado (mudança da API de terceiro), o serviço loga um aviso e trata como indisponível, em vez de misinterpretar silenciosamente um campo ausente/de tipo errado. Ao adicionar um campo novo lido da resposta da SerpAPI, adicione-o ao schema Zod também, não só ao código que o lê.

## Performance — obrigatório em qualquer alteração

Este serviço tem uma característica diferente dos outros três: o "hot path" não é uma request HTTP de alta concorrência, é um **job em lote que roda uma vez por hora e paga por chamada externa** (SerpAPI e Google Places são APIs pagas/limitadas). Performance aqui é tanto sobre latência quanto sobre **custo e consumo de cota das APIs externas**.

1. **O loop principal do job é sequencial de propósito** (`for...of` em `MovementService.updateMovementLevelsFromSavedEstablishments`, `await` por estabelecimento, sem `Promise.all`) — isso evita rajadas simultâneas contra a SerpAPI (rate limit/custo por chamada) e mantém o `try/catch` isolado por estabelecimento. Não paralelize esse loop com `Promise.all` sem antes considerar o rate limit real da SerpAPI; se for preciso ganhar throughput, prefira concorrência limitada (ex.: fila com N workers) a paralelismo irrestrito.
2. **Falha em um estabelecimento nunca derruba os demais**: o `try/catch` dentro do loop (`this.logger.error("[ERRO] Falha ao atualizar ${establishment.name}", error)`) garante isolamento — preserve esse padrão ao adicionar qualquer etapa nova dentro do loop.
3. **A busca inicial de estabelecimentos passa por `listEstablishmentsWithFallback`** (`MovementService`): se `listOpenEstablishments` falhar, o serviço reusa a última lista de estabelecimentos buscada com sucesso (guardada em memória, `lastKnownEstablishments`) em vez de abortar o ciclo inteiro — só propaga o erro (abortando o ciclo) se nunca houve uma lista bem-sucedida antes (ex.: primeira execução após o deploy). Esse cache é por processo/réplica e não sobrevive a um restart — não é uma fonte de verdade, é só uma rede de segurança para não perder um ciclo inteiro por uma falha pontual de rede no `establishment-service`.
4. **`isRunning` (boolean, em `movement.job.ts`) impede sobreposição de execuções**: se uma rodada demorar mais de uma hora, a próxima é pulada (log de aviso) em vez de rodar em paralelo — preserve essa guarda ao alterar a frequência do cron ou a lógica do job.
5. **Réplica única, sem lock distribuído**: `k8s/deployment.yaml` fixa `replicas: 1` e não existe `HorizontalPodAutoscaler` neste serviço. Isso não é incidental — o cron roda **dentro do processo** (`node-cron`), então subir mais réplicas faria o job hourly rodar uma vez por réplica, duplicando chamadas pagas à SerpAPI/Google e duplicando eventos Kafka de movimento. **Nunca aumente `replicas` deste deployment sem antes** extrair o job para um `CronJob` dedicado do Kubernetes ou adicionar um lock distribuído (ex.: advisory lock do Postgres, ou uma chave no Redis se ele for introduzido).
6. **Cache em memória (`TTLCache`) não é compartilhado entre réplicas/processos** e é perdido a cada restart — está OK com réplica única, mas não deve ser usado como argumento para aumentar réplicas sem resolver o ponto 5 acima; e não deve ser tratado como fonte de verdade (é só para reduzir chamadas repetidas dentro da janela de TTL).
7. **Publicação Kafka é síncrona dentro do loop** (`await kafkaProducer.send(...)` em `saveCurrentPopularity`, logo após o `upsert`) — cada estabelecimento só avança para o próximo depois do ack do broker. Aceitável no volume atual (job horário, não é request de usuário), mas se o número de estabelecimentos crescer para milhares, considere agrupar em batches (`messages: [...]` já suporta múltiplas mensagens por `send`) em vez de um `send` por estabelecimento.
8. **`cleanOldPopularTimesDaily` roda em toda execução do job** (antes do loop principal) e depende do índice `@@index([capturedDate])` — mantém `POPULAR_TIMES_RETENTION_DAYS` (28 dias) de histórico, o mínimo necessário para o fallback (item 3 da Responsabilidade) conseguir juntar até 4 amostras do mesmo dia da semana. No volume atual (dezenas de estabelecimentos × 24h × 28 dias) isso é trivial em espaço; sem tabela de agregado — decisão deliberada, não introduza uma antes de o volume de estabelecimentos justificar (milhares). Se o volume crescer muito além disso, considere particionamento por data em vez de só aumentar a frequência/alcance do `deleteMany`.
9. **`getFallbackSamples` depende do índice composto `@@index([establishmentId, dayOfWeek, hour])`** — qualquer nova consulta sobre `popular_times_daily` deve reaproveitar esse índice (mesma combinação de colunas) em vez de introduzir uma nova consulta sem índice de suporte. Esse método faz `findMany` (não `aggregate`) porque `computeMovement` precisa das amostras individuais (mediana, contagem para o `confidence`), não só a média.
10. **Uma leitura extra (`prisma.currentPopularity.findUnique`, select restrito a `score`/`level`) acontece por estabelecimento a cada ciclo**, antes de calcular o movimento — é o estado anterior usado para suavização (EMA) e histerese em `computeMovement`. Aceitável no volume atual (mais uma query rápida por estabelecimento, já sequencial); se o número de estabelecimentos crescer para milhares, considere buscar esse estado em lote (uma query com `establishmentId IN (...)`) em vez de uma consulta por estabelecimento.
11. **`$transaction([...])` em forma de array** (não callback interativo) é usada em `savePopularTimesDaily` para tornar o delete+insert do dia atômico — mantenha a forma de array para transações simples como essa; não troque por `$transaction(async (tx) => ...)` sem necessidade, pois isso mantém a conexão aberta por mais tempo.
12. **Reaproveitar singletons**: Prisma (`src/prisma/index.ts`, pool com `max` configurável via `DB_POOL_MAX`, default 10) e Kafka producer (`src/kafka/producer.ts`, lazy singleton) — nunca instancie um novo `PrismaClient`/`Kafka` client dentro de um service.

## Observabilidade

- `src/config/metrics.ts` — `Registry` próprio (`prom-client`), exposto em `GET /metrics` (sem `authenticate`, ver `server.ts`) — mesmo padrão do `establishment-service`. Inclui `collectDefaultMetrics` (métricas do processo Node) + `http_requests_total`/`http_request_duration_seconds` (via hooks `onRequest`/`onResponse` em `server.ts`, mesma implementação do `establishment-service`) + as métricas específicas do job abaixo.
- Métricas do job/scraping (todas em `src/config/metrics.ts`, incrementadas em `MovementService`/`SerpApiService`):
  - `scraping_cycle_duration_seconds` — duração de um ciclo completo (`updateMovementLevelsFromSavedEstablishments`);
  - `scraping_establishments_total` (gauge) — quantidade de estabelecimentos abertos no último ciclo;
  - `scraping_success_total` / `scraping_failure_total` — por estabelecimento, sem exceção vs. com exceção (isolamento de falha já existente, ver Performance #2);
  - `scraping_external_api_latency_seconds{api="serpapi"}` — latência da chamada à SerpAPI (em torno do `fetchWithTimeout` em `SerpApiService.fetchPopularity`);
  - `movement_calculation_total{level, source}` — contagem por nível calculado e origem (`LIVE`/`ESTIMATED`/`UNAVAILABLE` — rótulo de métrica, não o mesmo enum `source` persistido no banco);
  - `movement_confidence{source}` — histograma do `confidence` calculado por `computeMovement`;
  - `cache_hit_total{cache}` / `cache_miss_total{cache}` — `cache="movement"` (`MovementService.movementCache`) e `cache="serpapi"` (`SerpApiService.cache`).
- **Resumo de ciclo em log único**: ao final de `updateMovementLevelsFromSavedEstablishments`, uma linha de `info` agrega `total`/`sucesso`/`estimado`/`indisponivel`/`falha`/`skip`/`duracao` — não é preciso mais fazer grep de N linhas por estabelecimento para saber como um ciclo foi; preserve essa linha ao adicionar uma etapa nova ao loop.
- Não adicione instrumentação HTTP duplicada por rota — os hooks globais em `server.ts` já cobrem toda requisição; para uma métrica de negócio nova, registre um `Counter`/`Histogram` novo em `metrics.ts` reaproveitando o `register` existente (mesma orientação do `establishment-service`).

## Testes

- `npm test` — Vitest, roda `src/**/*.test.ts` (unitários co-localizados em `__tests__`) + `tests/**/*.spec.ts` (integração via `app.inject`).
- `npm run test:coverage` — cobertura de `src/services`, `src/controllers`, `src/routes.ts`, com thresholds mínimos **70% linhas, 70% funções, 60% branches** (mesmo padrão dos outros serviços) — não reduza para fazer um PR passar.
- `tests/setup/vitest.setup.ts` faz `vi.mock('../../src/config/env', ...)` **globalmente para todos os testes** (via `setupFiles`) — qualquer teste que precise de um valor de env diferente do default ali definido precisa remockar localmente (ver `vi.hoisted` + `vi.mock` no topo de `serpapi.service.test.ts`/`google-places.service.test.ts`), não editar o mock global para um caso específico.
- `tests/integration/scrapping.integration.spec.ts` é hoje o único arquivo de integração, cobrindo as 4 rotas (`/health`, `/places/:placeId/popularity`, `/movements/:establishmentId`, `/places/nearby`) com mocks de `SerpApiService`, `MovementService`, `GooglePlacesService` e `prisma` — siga o mesmo padrão de mocks (`vi.hoisted` + `vi.mock`) ao adicionar uma rota nova. `GET /places/nearby` tem 3 mocks distintos no mesmo teste (`mockSearchNearbySerpApi` no lugar de `SerpApiService.searchNearbyPlaces`, `mockSearchNearby` no lugar de `GooglePlacesService.searchNearbyPlaces`) cobrindo caminho principal, fallback (SerpAPI falha → Google responde) e falha total (os dois falham) — ao mexer nesse fallback, preserve os três casos.
- `src/jobs/__tests__/movement.job.test.ts` cobre `startMovementJob`: expressão/timezone do cron, a guarda `isRunning` (tick pulado enquanto o anterior está em andamento), isolamento de erro com reset de `isRunning` no `finally` (o próximo tick roda normalmente mesmo depois de uma falha), reuso do mesmo `MovementService` entre ticks, e o `stop()` retornado. Mocka `node-cron` (`cron.schedule`) capturando o callback agendado pra invocar diretamente em vez de esperar um tick real — siga esse padrão (`vi.hoisted` + mock do `MovementService` via `function` normal, não arrow function, já que precisa ser usada com `new`) ao alterar esse arquivo.
- `scripts/test-update-movement.ts` roda o job uma vez contra infra real — é um script de debug manual, não faz parte de `npm test` e não tem assertions; não confunda com os testes reais ao avaliar cobertura.
- `src/services/__tests__/movement-engine.test.ts` testa `computeMovement`/`computeFreshness` isoladamente (sem mockar Prisma/Kafka) — cobre suavização (EMA), histerese (troca pequena vs. grande, sem previousLevel, com previousLevel UNAVAILABLE), o caminho estimado (mediana, confidence escalando com nº de amostras) e os limiares de freshness. Prefira adicionar um teste novo aqui ao ajustar qualquer constante do algoritmo (`SMOOTHING_ALPHA`, `HYSTERESIS_MARGIN`, `MIN_HISTORICAL_SAMPLES`, `FRESH_MAX_MINUTES`, `STALE_MAX_MINUTES`) em vez de só em `movement.service.test.ts`, que cobre a integração (wiring do `previous` vindo do banco) mas não todos os casos do algoritmo.

Toda feature nova no pipeline do job precisa de: teste unitário no `MovementService` cobrindo o caminho feliz, o fallback por histórico, o caso `UNAVAILABLE`, e o isolamento de falha por estabelecimento (seguir os testes já existentes em `movement.service.test.ts`); mudanças no algoritmo de movimento em si (score/nível/confidence/freshness) precisam de teste em `movement-engine.test.ts`. Toda rota nova precisa de teste de integração cobrindo autenticado/não autenticado (quando aplicável) e o branch de erro.

## Variáveis de Ambiente

- Todas as env vars são lidas e validadas em `src/config/env.ts` via `zod.safeParse` + `process.exit(1)` em caso de falha — mesmo padrão do `establishment-service`. Ao adicionar uma env var nova, adicione-a ao `envSchema` em `env.ts` (não leia `process.env` direto em outro arquivo novo).
- **Exceção já existente** (não replique para variáveis novas): `src/prisma/index.ts` importa `"dotenv/config"` por conta própria e lê `process.env.DATABASE_URL`/`process.env.DB_POOL_MAX` diretamente, em vez de importar `env` de `config/env.ts` — mesmo tipo de exceção pontual observada no `user-service`. Essas duas variáveis, portanto, **não passam pela validação Zod de `env.ts`** (o Prisma falha por conta própria se `DATABASE_URL` for inválida).
- `JWT_EXPIRES_IN`/`JWT_REFRESH_EXPIRES_IN` (`env.jwtExpiresIn`/`env.jwtRefreshExpiresIn`) são lidas em `env.ts` (opcionais) mas **não são usadas em lugar nenhum do código** — este serviço só verifica tokens (`request.jwtVerify()`), nunca assina/emite JWT, então não há `expiresIn` a aplicar. Não assuma que essas variáveis têm efeito hoje; se for implementar emissão de token aqui (não é o padrão atual), é nesse ponto que elas passariam a ser usadas.
- `CORS_ORIGIN` tem default `"*"` no schema (ver Segurança #2) — é uma decisão deliberada de não quebrar o boot por isso, não um esquecimento; defina explicitamente em produção.
- `KAFKA_BROKERS` (`"kafka:9092"`), `CORS_ORIGIN` (`"*"`), `PORT` (`3000`), `RATE_LIMIT_MAX` (`100`) e `RATE_LIMIT_TIME_WINDOW` (`"1 minute"`) têm default no `envSchema`; `TZ` é opcional sem default (cai para o timezone do sistema operacional — ver `node-cron`/`Intl.DateTimeFormat`, não é uma falha). `JWT_SECRET`, `DATABASE_URL`, `SERP_API_KEY`, `GOOGLE_API_KEY` e `ESTABLISHMENT_SERVICE_URL` são **obrigatórios** e derrubam o boot se ausentes/inválidos (ver Segurança #1).
- Sem `.env.example` neste serviço hoje — se for criar um, siga o padrão de placeholders do `auth-service`.
- Propague toda env nova no `k8s/deployment.yaml` (hoje tudo vem via `envFrom: secretRef: scrapping-service-secret` — não há `configMapRef` neste serviço, diferente dos outros).

## Infra deste Serviço

- `Dockerfile`: build em 2 estágios (`builder` → `production`). Como o `generator client` do Prisma usa `output = "../src/generated/prisma"` (dentro de `src/`, não no local padrão), o `builder` precisa copiar manualmente esse diretório gerado para `dist/src/generated/prisma` depois do `tsc` (`RUN mkdir -p dist/src/generated && cp -r src/generated/prisma dist/src/generated/prisma`) — se o `output` do generator mudar, esse passo do Dockerfile precisa mudar junto, senão o build quebra silenciosamente em runtime (client ausente).
- O estágio `production` recria um `prisma.config.mjs` mínimo via `printf` inline no próprio `Dockerfile` (não copia o `prisma.config.ts` do repo) — necessário só para o `prisma migrate deploy` funcionar na imagem final. Se `prisma.config.ts` mudar (ex.: novo caminho de schema/migrations), esse bloco `printf` precisa ser atualizado manualmente em conjunto.
- `CMD` roda `prisma migrate deploy && node dist/src/server.js` — migration aplicada automaticamente no start do container (mesmo padrão do `auth-service`/`establishment-service`, diferente do `user-service`).
- `k8s/`: só existem `deployment.yaml` e `service.yaml` — **não há** `hpa.yaml`, `pdb.yaml`, `NetworkPolicy` nem `CronJob` neste serviço. `replicas: 1` fixo (ver Performance #5 — não é um detalhe incidental, é uma dependência real do design atual do job). Probes (`readinessProbe`/`livenessProbe`) apontam ambas para `/health` (checagem só de banco), sem endpoint `/ready` separado.
- `docker-compose.yml` local sobe Postgres (`scrapping_db`, porta host `5435`) **e Kafka** (`scrapping_kafka`, porta host **`19092`**, não `9092`) — o Kafka é próprio deste serviço, configurado com `KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:19092`, porque o job/scripts rodam via `npx tsx`/`npm run dev` **direto na máquina**, não dentro de um container — um Kafka configurado pra advertise só via hostname interno da rede Docker (ex.: o do `feed-service`, `PLAINTEXT://kafka:9092`) falha para esse caso: o bootstrap inicial funciona, mas a metadata de partição devolvida aponta pro hostname interno, que não resolve fora do Docker (`ENOTFOUND kafka`). **A porta host é `19092`, não `9092`, por um motivo real e específico deste ambiente (Windows + Docker Desktop)**: em teste, a porta `9092` no host mostrou port-forwarding cruzado — o cliente rodando na máquina recebia metadata de outro broker Kafka (nodeId/tópicos de outro serviço já usado no monorepo), mesmo com `docker ps` confirmando só o nosso `scrapping_kafka` publicado nela; recriar o container não resolveu, só trocar a porta do host resolveu. Se isso voltar a acontecer (ou em outra máquina), suspeite de uma regra de port-forward "presa" no Docker Desktop/WSL2, não do nosso `docker-compose.yml`. Não reaproveite o Kafka de outro serviço do monorepo para testar o job deste aqui sem confirmar o `ADVERTISED_LISTENERS` primeiro. `KAFKA_AUTO_CREATE_TOPICS_ENABLE: true` neste compose evita precisar de um `kafka-init` só pra criar o tópico `establishments`. `ESTABLISHMENT_SERVICE_URL` continua precisando apontar pra uma instância real (ou um stub HTTP simples respondendo `GET /establishments/open`) — não faz parte deste compose.
- CI/CD (`.github/workflows/scrapping-service.yml`): só roda `npm test` (sem um passo separado de `test:integration` ou `test:coverage` no pipeline), builda e publica no GHCR, e faz deploy via `kubectl set image deployment/scrapping-service ...` — não usa Helm nem `kubectl apply` de manifests neste workflow.
